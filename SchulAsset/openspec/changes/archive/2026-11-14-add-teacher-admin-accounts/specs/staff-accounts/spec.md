## ADDED Requirements

### Requirement: Only admins can create logins
The Edge Function `create-staff-account` SHALL create logins only for callers who are logged in with the role `admin`, and SHALL refuse everybody else (not logged in, `teacher`, `student`).

#### Scenario: Admin creates a login
- **WHEN** an admin calls the function with a valid e-mail and the role `teacher`
- **THEN** a login with that e-mail and the role `teacher` exists and the generated password is returned

#### Scenario: Teacher or student calls it
- **WHEN** a user with the role `teacher` or `student` calls the function
- **THEN** it answers "Forbidden" and creates nothing

#### Scenario: Not logged in
- **WHEN** the call carries no valid login
- **THEN** it answers "Unauthorized" and creates nothing

### Requirement: Roles that can be created
The function SHALL accept the roles `teacher` and `admin` only, and SHALL set the role in `user_roles` for the new login.

#### Scenario: Admin login
- **WHEN** the role `admin` is requested
- **THEN** the new user can log in and is routed to the admin area

#### Scenario: Unknown role
- **WHEN** another role (for example `student`) is requested
- **THEN** that entry is refused with an error and nothing is created for it

### Requirement: Existing accounts are never changed
If the e-mail address is already registered, the function SHALL refuse that entry with the message "E-Mail ist bereits registriert" and SHALL NOT change that account's password, role or any other property. It SHALL also refuse addresses ending in `@schulasset.local`.

#### Scenario: E-mail of an existing admin
- **WHEN** an admin asks for a teacher login with the e-mail of an existing admin
- **THEN** the entry is refused and the existing admin's password and role are unchanged

#### Scenario: iPad portal address
- **WHEN** the e-mail is `DMP123@schulasset.local`
- **THEN** the entry is refused

#### Scenario: Invalid address
- **WHEN** the e-mail is not a valid e-mail address
- **THEN** the entry is refused with an error

### Requirement: Generated passwords
Passwords SHALL be generated by the function from a cryptographically secure random source, be at least 12 characters long and avoid look-alike characters, and SHALL be returned only in the response to that call. They SHALL NOT be stored or logged.

#### Scenario: Different passwords
- **WHEN** two logins are created
- **THEN** their passwords differ and each is returned exactly once

### Requirement: Batches with per-entry results
The function SHALL accept 1 to 50 entries per call and SHALL return a result for each entry, either the password or an error, so that one failing entry does not stop the others. A call with more than 50 entries SHALL be refused.

#### Scenario: One bad entry in a batch
- **WHEN** a batch of three contains one already registered e-mail
- **THEN** the other two logins are created and the result lists the error for the third

### Requirement: No half-made accounts
If a step after creating the user fails (setting the role, writing the link), the function SHALL delete the user again and report an error for that entry.

#### Scenario: Role cannot be saved
- **WHEN** saving the role fails for a new user
- **THEN** that user no longer exists afterwards and the entry shows an error

### Requirement: A Lehrkraft can be linked to a login
`staff` SHALL have the columns `user_id` (unique, references the login, cleared when the login is deleted) and `login_email`. When an entry has a `staff_id`, the function SHALL set both columns on that Lehrkraft. It SHALL refuse a `staff_id` for the role `admin`, a `staff_id` that does not exist, and a Lehrkraft that already has a login.

#### Scenario: Linked Lehrkraft
- **WHEN** a teacher login is created with the `staff_id` of a Lehrkraft without login
- **THEN** that Lehrkraft shows the login's e-mail and the link to the login

#### Scenario: Lehrkraft already has a login
- **WHEN** the `staff_id` belongs to a Lehrkraft with a login
- **THEN** the entry is refused and no new login is created

#### Scenario: Login deleted in Studio
- **WHEN** the login of a linked Lehrkraft is deleted in Supabase
- **THEN** the Lehrkraft remains and has no login any more

### Requirement: Database changes are logged
The SQL for the new columns and the grant, and the deploy and test steps of the function, SHALL be recorded in `supabase/db-changes.md`.

#### Scenario: Log entry
- **WHEN** the change is finished
- **THEN** `supabase/db-changes.md` contains the SQL and how to deploy the function
